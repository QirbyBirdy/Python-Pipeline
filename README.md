# GLFS Data Cleaning & Imputation Pipeline

Bureau of Statistics — Guyana, Analytical Unit Technical Capability Assessment.
Dataset: GLFS 2017 Q4 microdata (round 174), two tracks — individual records (`ind`)
and the household emigration module (`emig`).

## Status: Week 1 (exploration & project setup)

Done:
- Project skeleton with split scripts (`Scripts/`)
- Both datasets ingested and validated against their data dictionaries
- Exploratory diagnostics for every column of both datasets
- Auto-drafted problem inventory (severity-ranked, descriptive only)

Not started yet (later weeks): cleaning, imputation, data dictionary, multi-format
export, automated Word report. See `docs/superpowers/specs/` and
`docs/superpowers/plans/` for the design and implementation plan this phase followed.

## Folder layout

```
Data/                       raw GLFS CSVs + data dictionaries + methodological report (never edited in place)
Scripts/
  config.py                 every path used by the pipeline, in one place
  glfs_pipeline/
    ingest.py                stage 1: raw CSV -> validated -> interim parquet
    diagnostics.py            stage 2: per-column diagnostics (missingness, uniqueness, label-set)
    problem_inventory.py      stage 3: auto-drafted, severity-ranked findings
  run_pipeline.py            single entry point, runs all stages for one or both datasets
Outputs/
  interim/                  working-copy parquet cache (gitignored, regenerated by ingest)
  diagnostics/               diagnostics CSV + markdown report per dataset
  problem_inventory/         drafted problem-inventory markdown per dataset
reports/                     weekly Friday progress reports
presentation/                final PowerPoint (Week 3)
```

`Data/`, `Scripts/`, and `Outputs/` play the role the assessment brief calls
`raw/`, the pipeline code, and `outputs/` respectively — kept as-is rather than
renamed, since they were already in place and working before the brief's exact
naming convention was confirmed.

## Setup

```bash
python -m pip install -r requirements.txt
```

## Running the pipeline

```bash
python Scripts/run_pipeline.py                 # both datasets
python Scripts/run_pipeline.py --dataset ind    # individual records only
python Scripts/run_pipeline.py --dataset emig   # emigration module only
```

This runs ingest -> diagnostics -> problem_inventory in order and writes every
output under `Outputs/`. Each stage is a plain function taking `(name,
datasets_dict)`, so any stage can also be run directly against `config.DATASETS`
for debugging.

## Architecture notes

Each pipeline stage is its own module under `Scripts/glfs_pipeline/` rather than
flat numbered scripts (`01_ingest.py`, `02_diagnose.py`, ...) — a package-style
layout was chosen because later weeks add several more stages (cleaning is
expected to split into multiple issue-class scripts, plus imputation, export,
and report generation), and grouping them as an importable package keeps
`run_pipeline.py` as a single readable entry point instead of a long shell
script chaining separate files. Reproducibility is unaffected: `python
Scripts/run_pipeline.py` is still the one command that produces every output.

No cleaning or value transformation happens in this phase. `diagnostics.py` and
`problem_inventory.py` are read-only with respect to the data — they report and
rank issues, they do not fix them.

One data-quality note surfaced during diagnostics: the data dictionaries'
`choices` column names a Stata value-label *set* (e.g. `yesno`, `Sex`), not an
enumerated list of valid codes, and the `ind` dataset has no `.dta` file to
resolve real label mappings from. Diagnostics reports the label-set name for
context only and does not attempt to validate observed values against it.
